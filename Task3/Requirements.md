# Требования к внешним интеграциям «Умный дом»

## 1. Требования к безопасности

- **Минимизация данных (Data Minimization):** PropDevelopment не должен передавать партнёру полные профили (ФИО, телефоны). Партнёру передаются только обезличенные идентификаторы (ID жильца), хеш-коды биометрии (или фото-векторы, если партнер осуществляет распознавание) и номера автомобилей.
- **Защита персональных данных (ПДн):** Если платформа партнёра хранит биометрические данные или номера авто, партнёр обязан юридически и технически соответствовать требованиям законодательства РФ (152-ФЗ, ЕБС), а передача данных осуществляется только после подписания согласия (DPA) пользователем в приложении PropDevelopment.
- **Изоляция арендаторов:** Идентификаторы жилых комплексов и пользователей должны быть криптографически непредсказуемыми (UUIDv4), чтобы предотвратить атаки типа IDOR/BOLA со стороны систем партнёра.
- **Шифрование данных:** Все интеграционные потоки между PropDevelopment и платформой партнёра должны передаваться по протоколу TLS версии не ниже 1.2 (рекомендуется 1.3).
- **Аудит и логирование:** Все события обмена данными, изменения прав доступа и факты физического открытия дверей должны логироваться в системах PropDevelopment (без записи чувствительных данных в открытом виде) для расследования инцидентов.

## 2. Аутентификация и авторизация

- **Система-Система (Backend-to-Backend):** Взаимодействие между сервисом «Умный дом» (PropDevelopment) и платформой партнёра должно осуществляться с использованием mTLS (Mutual TLS) для двусторонней аутентификации серверов. Дополнительно можно использовать подписанные JWT-токены сервисных аккаунтов.

- **Пользователь-Приложение:** Доступ из мобильного приложения к функциям умного дома должен осуществляться по протоколу OAuth 2.0 / OpenID Connect. Приложение получает короткоживущий Access Token.

- **Управление правами (Authorization):** Провайдером идентификации (IdP) и источником истины (Source of Truth) выступает CRM PropDevelopment. Партнёрская платформа осуществляет доступ на основе ролевой модели (RBAC), получая от PropDevelopment только необходимые статусы (разрешен/запрещен).

## 3. Взаимодействие и протоколы

- **Backend-to-Backend архитектура:** Мобильное приложение никогда не взаимодействует с API партнёра напрямую. Все запросы (например, «открыть дверь») идут от приложения в API Gateway PropDevelopment, откуда внутренний микросервис проксирует команду партнёру. Это защищает ключи интеграции и позволяет применять единые политики ИБ.

**Асинхронный обмен (События):** Для передачи информации о физических событиях (например, камера распознала номер и шлагбаум открылся) используется событийно-ориентированная модель. Платформа партнёра отправляет Webhook-уведомления в API PropDevelopment, либо используется брокер сообщений (например, Kafka/RabbitMQ), если между компаниями организован выделенный VPN-туннель.

**Синхронный обмен (Команды):** Для пользовательских команд из приложения (нажатие кнопки «Открыть») используется синхронный REST API (или gRPC), так как пользователю требуется моментальный отклик интерфейса.

**Синхронизация белых списков:** PropDevelopment регулярно (через планировщик) или по триггеру (при добавлении новой машины жильцом) обновляет списки разрешенных номеров авто на стороне партнёра, чтобы при отключении интернета шлагбаумы могли работать автономно (Edge Computing).
